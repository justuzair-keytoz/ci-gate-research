## 1. Change detection

Four real options, not really competing on the same axis:

| Tool                                | What it does                                                                                                       | Needs                                    |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------- |
| **dorny/paths-filter**              | Matches changed file paths against glob rules you define, per job                                                  | Just git, works with any package manager |
| **turbo run --filter / --affected** | Understands your dependency graph (via `turbo.json`), only runs tasks for affected packages _and their dependents_ | Turborepo adopted in the repo            |
| **nx affected**                     | Same idea, broader language support (Go, Rust, Java, not just JS/TS)                                               | Nx adopted in the repo                   |
| **yarn workspaces foreach --since** | Yarn 4's own affected-package detection, built in (no plugin needed on v4)                                         | Nothing extra — you already have this    |

Key distinction: **paths-filter matches file globs you write by hand; turbo/nx understand the dependency graph automatically.** If package A imports package B, and only B changed, paths-filter won't catch that A needs testing too unless you've manually listed A's dependency in its filter rule. Turbo and Nx do this by walking the actual `package.json` dependency tree.

For a codebase with 14 services and cross-package imports (which your `@remixicon/react` failure case in PR #297 suggests is common), this matters — paths-filter's glob rules would need manual upkeep as services gain dependencies on shared packages, or you'd risk under-testing.

Both tools need full git history to compare against, not the shallow clone GitHub Actions does by default: `fetch-depth: 0` is required for either Turborepo and Nx both need git history to compare changes, and GitHub Actions checkout does a shallow clone with fetch-depth: 1 by default, so fetch-depth: 0 is needed for full history or enough depth to reach the merge-base.

**On `--since`:** this is Yarn's own affected-detection, no extra tool needed. It's real but blunter than turbo/nx — it detects "this workspace's files changed" via git diff against a base ref, not "this workspace is affected by the dependency graph." It won't automatically pull in a workspace that only depends on something changed, unless yarn's own dependency resolution triggers that (it does account for workspace `dependencies`, but the mechanism is simpler than turbo/nx's task graph).

**What's newer here (2026):** turbo's `--affected` flag ships as a first-class replacement for the older `--filter='...[origin/main...HEAD]'` syntax, and computes the same thing with less boilerplate — by default, --affected is equivalent to --filter=...[main...HEAD], considering changes between main and HEAD, but requires everything between base and head to exist in the checkout. This is a syntax simplification, not a new capability.

**Recommendation to weigh:** since Yarn 4 workspaces are already in place and turbo/nx are not mentioned as adopted, `yarn workspaces foreach --since` is the lowest-friction starting point — zero new tooling. Layer `dorny/paths-filter` on top _only_ for the Docker-build gating (deciding which services' Dockerfiles to build), since that's a build-artifact decision, not a package-dependency one, and paths-filter's explicit glob rules make "which Dockerfile touches which paths" auditable in one file. Adopting turbo or nx purely for this gate is probably more machinery than the problem needs — that's a bigger call than a CI gate, since it changes how every developer runs `yarn build`/`yarn test` locally too. **Question for you:** is turbo or nx already used anywhere in the repo (a `turbo.json` or `nx.json`)? That changes this recommendation.

## 2. Matrix strategy: dynamic vs static

**Dynamic** — a "prepare" job runs paths-filter/yarn --since, emits a JSON array of affected services, and a downstream job consumes it via `strategy.matrix: ${{ fromJson(...) }}`. Example pattern:

```yaml
detect:
  outputs:
    packages: ${{ steps.affected.outputs.packages }}
  steps:
    - id: affected
      run: |
        PACKAGES=$(yarn workspaces foreach --since --json ... )
        echo "packages=$PACKAGES" >> $GITHUB_OUTPUT
test:
  needs: detect
  strategy:
    matrix:
      package: ${{ fromJson(needs.detect.outputs.packages) }}
```

**Static** — every service gets a named job up front, each starting with `if: needs.detect.outputs.<service> == 'true'`.

Trade-offs, plainly:

- **Dynamic** scales cleanly as services are added — no workflow file edits. But job names in the GitHub UI become anonymous (`test (UI)`, `test (Strapi)` — fine) and, critically, **dynamic matrix job names can't be pinned as required status checks**, because the check name only exists after the matrix expands, and GitHub's branch protection UI needs a name to point at up front. This is what forces the aggregating gate job (next section) — it's not optional once you go dynamic.
- **Static** gives you readable, stable job names you can directly mark required in branch protection, no aggregating gate needed for _that_ problem. But it means editing the workflow file every time a service is added, and it doesn't scale past a handful of services without becoming unreadable.

With 14 services, static matrix means a 14-branch `if` chain that's edited on every new service — that's exactly the kind of drift that got you to "14 workflows, manual-only" in the first place. Dynamic is the standard choice at this scale in every source I found; nobody keeps a static per-package matrix past a small handful of packages. One practical note worth designing around explicitly: pin the comparison SHA in the prepare job (`git merge-base origin/main HEAD`), not a live `origin/main` reference, because someone might merge to main between the detect job and the test jobs, so pinning the merge-base SHA ensures the affected-package calculation stays consistent with what actually runs.

## 3. Required checks + dynamic matrix — the sharp edge, confirmed

This is real and well-documented, not a hypothetical. The core bug: jobs with a matrix configuration can be skipped from the top level before the matrix even expands, and if the inner-matrix jobs are required status checks, the pull request hangs forever waiting for a status that will never be reported. GitHub has had an open issue on this since 2021; it hasn't been fixed at the platform level.

**The standard fix**, confirmed across GitHub's own troubleshooting docs and community threads: add one more job after the matrix that always runs (via `if: always()`), depends on every matrix job, and reports success/failure based on their combined result. _That_ job — not the matrix jobs themselves — is what you mark as the required status check:

```yaml
gate:
  needs: [detect, test]
  if: always()
  runs-on: ubuntu-latest
  steps:
    - run: |
        if [[ "${{ contains(needs.*.result, 'failure') }}" == "true" ]]; then
          exit 1
        fi
```

This pattern appears independently in the actions/runner issue thread and a community-maintained fix documented by fkirc: if matrix jobs run conditionally and are set as required checks, you can add a subsequent job whose only task is to report the final status of the matrix, and register that final job as the required check instead.

There's a second, related problem worth distinguishing: **path-filtered workflows that don't trigger at all** on a given PR (not a skipped job inside a triggered workflow, but a whole workflow that never runs because no matching paths changed) will _also_ leave a required check stuck pending forever, because GitHub is waiting for a status that no run will ever post. GitHub's own docs describe the fix as a second, always-on workflow with the same job/check name that trivially passes when the first one's paths don't match: a generic workflow using paths-ignore, with the same job and check name, that returns true in any case, so the checks always pass when a PR doesn't change the files the primary workflow watches.

You need both mechanisms in this design: the aggregating gate job for the dynamic Docker-build matrix, _and_ the always-passing shadow workflow (or, more simply, structure things so the gate job itself always runs regardless of what triggered — which sidesteps needing two workflow files). I'd lean toward the second approach — one workflow, one gate job that's always present — since maintaining a duplicate "shadow" workflow file per real workflow is its own source of drift, similar to what got the repo into its current state.

## 4. Docker layer caching in Actions

Three real backends, plus what constraint A3 rules out.

**`type=gha` (GitHub Actions cache)** — no external service, no credentials, works immediately on GitHub-hosted runners. This is the only backend that needs _zero_ extra secrets. `mode=max` (cache every layer, not just the final stage) is the setting you want for multi-stage Dockerfiles: mode=max caches all layers including intermediate stages in a multi-stage build, using more storage but giving far more cache hits, since a change late in the Dockerfile can still reuse everything before it. The catch: it draws from the same Actions cache budget as your dependency caches, and eviction is LRU, so a large mode=max image cache can eat a big chunk of that budget and quietly cost you your dependency caches too once you exceed the limit. Worth knowing: GitHub raised the old hard 10GB-per-repo ceiling in late 2025 — repositories now get 10GB free by default, but org/repo admins can raise the limit beyond that on a pay-as-you-go basis, with least-recently-used eviction once the configured limit is hit. Given two multi-stage Dockerfiles (UI ~10min, API ~6min today per your numbers) plus dependency caches, you may want to check whether the default 10GB is enough or worth raising — that's a one-time admin setting, not something to build around in the workflow.

**`type=registry`** — cache stored as a tag in a container registry (GHCR, ECR, Docker Hub). Shared across workflows/repos, doesn't compete with the Actions cache budget, supports `mode=max` too. Needs a registry login step.

**ECR pull-through / ECR registry cache** — this is where **A3 conflicts with itself**. Both ECR-as-remote-cache and ECR pull-through mirroring require AWS credentials in the job that's building the cache — the remote cache feature requires Docker Buildx and logging in to ECR with AWS access credentials before the build step runs. A3 states PR runs get no AWS credentials at all. So ECR-backed caching (pull-through or registry) is not available under the constraints as written — not because it's a bad option, but because it needs exactly the AWS access A3 rules out. This isn't a blocker: `type=gha` needs no AWS access and is the standard default for this reason. But it's worth being explicit that "no AWS creds in PR runs" and "use ECR pull-through" can't both be true, in case A3 was written before this caching design was pinned down.

**Building without pushing** (relevant since A3 also says the gate never pushes to ECR): the standard pattern is `push: false, load: true`, which builds the image into the local Docker daemon so you can smoke-test it, without any registry auth at all:

```yaml
- uses: docker/build-push-action@v7
  with:
    push: false
    load: true
    cache-from: type=gha
    cache-to: type=gha,mode=max
```

This is exactly the shape used in real build-validation workflows — build, load locally, run a smoke test against the built image, never touch a registry. That satisfies A3's "no push" requirement cleanly and needs zero AWS setup, confirming `type=gha` + `push:false/load:true` is the right combination for this gate specifically.

**Recommendation:** `type=gha` with `mode=max`, `push: false`, `load: true`, and a cheap smoke test after build (container starts, responds to a health check, or `--version` runs) — not a full deploy-path replica. Registry-cache (GHCR, which the repo may already have access to via its GitHub org) is the upgrade path if the Actions cache budget becomes a bottleneck later; ECR options stay off the table unless A3 is revisited to allow a scoped, read-only AWS role via OIDC (short-lived tokens, no stored secrets) specifically for cache pull.

## 5. Monorepo CI conventions

**Concurrency & cancellation** — the standard pattern, confirmed across GitHub's own docs and independent write-ups:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: true
```

This satisfies A1's "cancel superseded runs on force-push" directly — it's not extra work, it's the default recommended shape for any PR-triggered workflow.

**Fail-fast** — for matrix jobs, `fail-fast: false` is usually what you want on a correctness gate: if the UI build fails, you still want to know whether the API build also fails, rather than the matrix aborting early and giving incomplete signal. GitHub's own guidance frames this directly: setting fail-fast to false prevents GitHub from cancelling all in-progress matrix jobs if any one of them fails. Given the stated purpose here ("optimize for main always deployable," not speed), full-matrix-on-failure is the right default — a PR failing both UI and API builds should say so, not just the one that failed first.

**PR-time vs merge-time boundary** — this is a real, long-standing distinction, not something new. LinkedIn's engineering blog on trunk-based CI at scale describes the standard split plainly: pre-merge validation and post-merge validation are both used to keep a high-velocity trunk stable, which is the norm for many trunk-based-development CI systems. The convention: expensive/slow checks (full e2e, deploy smoke tests) go post-merge or nightly; anything that would let a bad change land goes pre-merge. Your explicit exclusion of Playwright/e2e from this gate matches that convention exactly — it's not a shortcut, it's where most teams draw this same line.

**Merge queue** — explicitly out of scope for this task, but worth knowing where it sits conceptually, since "required checks + hard cut" is the precondition for it. GitHub's native merge queue and third-party options (Graphite, Mergify) all work the same way: a temporary branch combines the PR with the latest main, CI runs against that combined branch, and only if checks pass does the PR actually merge — this is what prevents two individually-green PRs from combining into a red main, which your aggregating gate alone doesn't protect against (that only protects a single PR against itself). Not needed for this task, but it's the natural next step once the gate is stable, exactly as your "done when" list already notes.

**What's genuinely new here (2026, post-AI-volume specifically):** a few sources converge on the same shift, worth citing plainly since it's the "how did the industry adapt" thread you asked for. As AI coding agents produce far more PRs per engineer, teams are restructuring CI into explicit tiers rather than one big job — one detailed architectural writeup frames it as a hierarchical validation pipeline broken into tiers by cost and failure probability: fast lint, dependency-graph checks and secret scanning first, then type-checking and targeted unit tests, with the full suite and image build only running once the fast tiers pass. This is precisely your hybrid design already, described independently. The same source specifically calls out dependency-hallucination as a top-tier check: verify that all imports exist in the package manifest without running a full install, since AI-suggested dependencies are a common failure mode — this is your PR #297 case exactly (`@remixicon/react` imported without being declared), and it's explicitly framed in current sources as a _fast, first-tier_ check, not something to catch later in a full build.

The other 2026 shift worth flagging: Base Power's engineering write-up (Aug 2026) on scaling merge queues for agent-driven PR volume describes footprint-based parallel merge queues, where only PRs with overlapping build-graph footprints get serialized against each other — if two changes' footprints are disjoint, neither can invalidate the other's green result, so they can merge concurrently instead of queueing behind each other, and in their measurements roughly 40% of merges skip re-validation entirely because nothing that landed since their base touched their footprint. This is explicitly the frontier, not the mainstream default — it requires the kind of hermetic, content-addressed build graph (they use Bazel) that a Yarn-workspaces monorepo doesn't have out of the box. Not relevant to this gate (merge queue is out of scope), but useful context if merge queue adoption comes up later: it's a meaningfully different approach than "just turn on GitHub's native merge queue," and worth a deliberate choice rather than a default when that day comes.
