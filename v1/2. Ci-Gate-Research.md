## 1. Context and constraints (from the task brief)

These come from the brief, not from research.

- Repo: private, GitHub. Next.js UI, Strapi, ~10 Node workers, Python services (RAG, Parser, Temporal, workflow-engine), Yarn 4 workspaces.
- Private company npm packages are pulled via a token in `.npmrc` (the `bharat-tech-labs` scope, `PACKAGE_REGISTRY_TOKEN`).

- Deploy path is a Docker build (`docker build -f UI/Dockerfile --target production`), not `yarn build`. Deploy is manual and stays that way.

- Design-session choices (listed in the brief, not researched here): correctness gate, all services path-filtered, hybrid depth (fast native checks + Docker build for touched services), hard cut.

## 2. Corrections to earlier notes in this session

Three things I said earlier need fixing after re-checking sources.

1. **"A skipped matrix job leaves a required check pending."** GitHub's docs are narrower. A whole workflow skipped by path/branch filtering or commit message stays Pending. A single job skipped by an `if:` reports Success. A job whose dependency failed is skipped and may not block the PR. [Docs: S1]. The "matrix legs skipped at top level" case is reported by users, but I could not re-open that thread. [Unverified]
2. **"ECR pull-through cache needs AWS creds, so it clashes with A3."** I mixed up two ECR features. What I researched is the BuildKit remote build cache stored in ECR, which needs push access to ECR [Docs: S19]. ECR pull-through cache is a different feature (mirrors upstream registries such as Docker Hub). I did not research it. [Synthesis]
3. **"Yarn `--since` accounts for dependents."** The Yarn docs say `--since` runs on workspaces modified since a ref. They do not say dependents are included [Docs: S10]. Two community plugins exist specifically to add "changed plus dependents" [Docs: S11, S12], which hints core does not do it. Test this in the POC.

## 3. Change detection: which services did this PR touch?

### 3.1 Options

| Option                                                      | How it decides                                                                 | Understands dependency graph?               | Needs adoption of a tool?               | Evidence                        |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------- | --------------------------------------- | ------------------------------- |
| `dorny/paths-filter`                                        | Matches changed files against glob rules you write                             | No. You list dependencies by hand           | No                                      | [Docs: S13]                     |
| `yarn workspaces foreach --since`                           | Workspaces modified since a git ref                                            | Not stated in docs (see section 2, point 3) | No, already in Yarn 4                   | [Docs: S10]                     |
| Yarn plugins (`changed`, `enhanced-workspaces`)             | Changed workspaces and their dependents                                        | Yes                                         | Adds a plugin                           | [Docs: S11, S12]                |
| `turbo run --affected` / `--filter`                         | Package graph from `turbo.json` and package.json                               | Yes                                         | Adopt Turborepo                         | [Docs: S7, S8]                  |
| `nx affected`                                               | Project graph                                                                  | Yes                                         | Adopt Nx                                | [Docs: S9]                      |
| Newer cross-language CLIs (example: `affected`, a Rust CLI) | Auto-detected dependency graph, lists Yarn Berry and Python among 7 ecosystems | Yes                                         | Extra binary; small project, not vetted | [Docs: S14, README claims only] |

### 3.2 Notes per option

**dorny/paths-filter**

- Works on `pull_request`, `push`, and `merge_group` events. `merge_group` support landed in v4 [Docs: S13].
- Latest release seen: v4.0.2, 2026-07-02 [Docs: S13, secondary page].
- Supply-chain note: a third-party scorer (StepSecurity) rates it 4/10 and flags low recent maintenance [Vendor: S13b]. If used, pin to a commit SHA. [Synthesis]
- Because it's glob-based, a change in `packages/shared` will not select a service unless you list that path in the service's filter. [Synthesis, follows from how globbing works]

**yarn workspaces foreach --since**

- Default refs come from the `changesetBaseRefs` config [Docs: S10].
- Older Yarn (v2/v3) needed the `workspace-tools` plugin; the Yarn 4 page I retrieved shows no plugin note [Docs: S10, S10b]. Confirm on your Yarn version. [Unverified]
- Combine with `-R` (recursive) to follow dependency fields instead of the `workspaces` field [Docs: S10]. What that does together with `--since` needs a POC test. [Synthesis]

**turbo --affected**

- Default equals `--filter=...[main...HEAD]` [Docs: S8].
- Needs git history between base and head. With a too-shallow checkout it falls back to treating everything as changed [Docs: S7, S8].
- Has a `prune` command for slim Docker images [Docs: S7]. Relevant to the Docker path, but it is a bigger change than CI.
- Can be combined with `--filter` (both must match) [Docs: S8].

**nx affected**

- Steps: git finds changed files, project graph maps files to projects, dependents are added [Docs: S9].
- Docs recommend using the last successful main commit as the base [Docs: S9].
- Docs say it works best with remote caching and distribution [Docs: S9].

### 3.3 Trade-offs that apply to all of them

- Every graph-based option needs full git history (`fetch-depth: 0` or enough depth to reach the merge base). [Docs: S7, S8, S9]
- Path-level GitHub triggers (`on.pull_request.paths`) should not be used for a required workflow. GitHub says a workflow skipped this way leaves its checks Pending and blocks merges [Docs: S1]. Detection inside the workflow avoids this. [Docs: S1 + Synthesis]
- Python services are not covered by Yarn/Turbo/Nx workspace graphs unless configured. Path-based detection handles them with no extra work. [Synthesis]
- Combos are common: a graph tool for JS packages plus path filters for the Docker/Python side. [Vendor: S21, and Synthesis]

- What does `--since` return for a PR that only touches `Dockerfile` or `.github/`?
- Is any of Turbo/Nx already in the repo (`turbo.json`, `nx.json`)? Unknown to me.

## 4. Matrix strategy

### 4.1 Options

**Dynamic matrix.** A first job outputs a JSON list of affected services. The next job reads it with `fromJson(...)` in `strategy.matrix`. GitHub documents this "output of one job defines a matrix" pattern [Docs: S5].

**Static matrix / static jobs.** Every service has a fixed job or matrix entry. Each starts with an `if:` that checks the detection output.

### 4.2 Trade-offs

|                                    | Dynamic                                                                        | Static                                                  |
| ---------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------- |
| Adding a service                   | Edit the detection config only                                                 | Edit the workflow                                       |
| Job names in the UI                | Come from matrix values                                                        | Fixed and readable                                      |
| Can be a required check by itself? | No practical way (names exist only after expansion) [Synthesis]                | Yes, but a skipped job still needs care (see section 5) |
| Fits 14 services?                  | Common choice at this size [Vendor: S21, Synthesis]                            | Grows long; hard to read [Synthesis]                    |
| Empty list                         | Matrix with no entries must be handled, or the job errors [Synthesis, test it] | No such case                                            |

### 4.3 Related settings

- `fail-fast` defaults to true: one failing leg cancels the others [Docs: S5]. For a gate that should show every broken service, `false` gives more signal [Synthesis].
- `max-parallel` limits simultaneous legs [Docs: S5].
- Pin the comparison SHA in the detect job (merge-base) and pass it to later jobs so results do not shift if main moves mid-run. [Vendor: S21, Unverified]

## 5. Required checks and the aggregating gate job

### 5.1 What GitHub says (official)

- Workflow skipped by path filter, branch filter, or commit message: its checks stay **Pending**; a PR requiring them is blocked [Docs: S1].
- Job skipped by an `if:` inside a running workflow: reports **Success** [Docs: S1].
- Job whose `needs` failed: skipped, does not report failure; the PR may not be blocked. To require a job that depends on others, add `always()` together with `needs` [Docs: S1].
- A check must have completed successfully in the repo within the last seven days to be selectable as required [Docs: S1]. Matters for first-time setup: run the gate at least once before adding it in branch protection. [Synthesis]
- If a check and a commit status share a name, both are required [Docs: S1].

### 5.2 Patterns

**A. Aggregating gate job.** One final job with `needs: [all others]` and `if: always()`. It inspects `needs.*.result` and fails if any is `failure` or `cancelled`. Only this job is marked required. Matches GitHub's `always()` advice [Docs: S1]. The exact script (which results count as pass: `success` and `skipped`) is a design choice. [Synthesis]

**B. Companion "always passes" workflow.** GitHub's own older docs show a second workflow with the same job name that returns success when the first is skipped by paths [Docs: S1, older version]. Works but means two files to keep in sync. [Synthesis]

**C. No trigger-level path filters.** Trigger the workflow on every PR, detect changes inside, skip jobs with `if:`. Then the workflow itself never gets skipped, and the gate job always reports. [Docs: S1 + Synthesis]

**D. Required check per static job.** Possible with a static layout; still needs `always()` handling for dependents of failed jobs [Docs: S1].

### 5.3 To check in the POC

- Empty detection result: does the gate go green with everything skipped?
- One leg fails, another is cancelled: does the gate go red?
- A leg is skipped by `if:`: gate should treat as pass. Confirm the gate script does.

## 6. Docker validation and layer caching

### 6.1 Build without push

Build with `push: false` and `load: true` so no registry login is needed. Build-and-smoke-test workflows using this shape exist in public repos. [Unverified: I saw a public example earlier but lost the link.] The `build-push-action` inputs themselves are standard. [Synthesis]

### 6.2 Cache backends

| Backend                                                                        | Where cache lives                    | Needs registry creds?        | Notes                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------ | ------------------------------------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `type=gha`                                                                     | GitHub Actions cache                 | No                           | Docs call it the recommended cache for GitHub Actions, within GitHub's size limits [Docs: S15]. Needs a non-default builder (docker-container driver) [Docs: S15]. Same page tags it experimental [Docs: S15]. Can hit API rate limits; supplying a GitHub token to BuildKit reduces that [Docs: S15]. |
| `type=registry`                                                                | A separate cache image in a registry | Yes (login to that registry) | Supports `mode=max` [Docs: S16]                                                                                                                                                                                                                                                                        |
| `type=inline`                                                                  | Inside the pushed image              | Yes (needs a pushed image)   | Supports only `min` mode [Docs: S16]                                                                                                                                                                                                                                                                   |
| ECR as registry cache                                                          | Cache image in ECR                   | Yes (AWS credentials)        | Needs `image-manifest=true` and `oci-mediatypes=true`; BuildKit 0.12+ [Docs: S19, Vendor: S20]                                                                                                                                                                                                         |
| `local`                                                                        | Directory on the runner              | No                           | Gone when the runner is gone unless saved through `actions/cache`. [Synthesis]                                                                                                                                                                                                                         |
| Paid build services / faster runners (Depot, Blacksmith, Namespace, WarpBuild) | Vendor-managed                       | Depends on vendor            | [Vendor]. Not researched in depth.                                                                                                                                                                                                                                                                     |

### 6.3 `mode=min` vs `mode=max`

`max` exports cache for all stages, `min` only the final image layers. Multi-stage Dockerfiles benefit from `max` [Docs: S16 covers that inline is min-only; the benefit for multi-stage is Synthesis].

### 6.4 GitHub cache size

- 10 GB per repo, free. Since Nov 2025 admins can raise it, pay-as-you-go, on Pro/Team/Enterprise plans. Default retention 7 days. Least recently used entries are evicted at the limit [Docs: S18].
- Docker layer cache shares this budget with dependency caches. [Synthesis, follows from S15 and S18]

### 6.5 How this meets the "no AWS creds in PR runs" assumption (A3)

- `type=gha` + `push: false` needs no AWS access. [Docs: S15, Synthesis]
- ECR-backed build cache needs AWS credentials [Docs: S19]. It would need a scoped role (for example via GitHub OIDC) if ever wanted. [Synthesis]
- Base images pulled from private registries or the private npm token in build args are separate concerns. Build args holding secrets can leak into layers and cache. Docker's cache docs warn about handling secrets with `COPY`/`ARG` [Docs: S17]. Look at BuildKit secret mounts for the token. [Synthesis]

## 7. Keeping the gate build and the deploy build the same

The gate's build only predicts deploy if both run the same command. Options, loosest to tightest. All [Synthesis]; the pattern names are common practice but I have no source for the ordering.

| Level | Idea                                                                                  | Guards against drift? | Touches deploy workflow?                                 |
| ----- | ------------------------------------------------------------------------------------- | --------------------- | -------------------------------------------------------- |
| 0     | Two separate inline `docker build` commands                                           | No                    | No                                                       |
| 1     | A check that reads both workflow files and compares the build flags                   | Detects drift         | No (read-only)                                           |
| 2     | One config file per service (Dockerfile path, target, build args) both workflows read | Shares data           | Small edit                                               |
| 3     | One shared composite action / script that both call                                   | Shares code           | One-line change to deploy                                |
| 4     | Build once in CI, push tagged by commit SHA, deploy promotes that image               | Same artifact         | Yes; changes what deploy does; needs push access from CI |

Note: Level 4 conflicts with A3 as written and with the "no deploy changes" scope. Levels 2-3 touch a file the brief lists as out of scope. That is a scope question for the team.

## 8. Pipeline conventions

### 8.1 Concurrency and cancellation

- `concurrency.group` with `cancel-in-progress: true` cancels older runs in the same group [Docs: S4].
- `cancel-in-progress` can be an expression, for example to skip cancelling on release branches [Docs: S4].
- Docs say ordering is not guaranteed between runs in a group [Docs: S4]. Fine for cancel-on-push; matters if used for deployments.
- Group by PR number or ref so each PR has its own group. [Synthesis]

### 8.2 Tiered checks

One 2026 blog describes tiers: fast checks first (lint, dependency check, secret scan), then type-check and targeted tests, then full suite and image builds only after earlier tiers pass. It also lists a fast check that every import exists in the package manifest [Blog: S22, re-open before relying]. This matches the brief's hybrid design and the PR #297 case (import without declared dependency). It is a single blog, not a standard. [Synthesis]

### 8.3 PR-time vs merge-time

- Common convention: keep PR-time checks fast and blocking; move slow checks (e2e, full deploy tests) to post-merge or nightly. LinkedIn's engineering blog discusses pre-merge and post-merge validation [Unverified: link lost]. DORA's trunk-based development pages cover similar ground [Unverified: link lost].
- The brief already puts e2e out of scope, consistent with this.

### 8.4 Merge queue (out of scope, reference only)

- A merge queue tests the PR merged with latest main plus PRs ahead of it, so two individually green PRs cannot combine into a red main. A gate alone does not do this. [Docs: S6 for mechanics; the "gate alone does not" reasoning is Synthesis]
- Workflows must also trigger on `merge_group`, or required checks never report in the queue and merges fail [Docs: S6]. Design the gate workflow with `merge_group` in mind now to avoid a rewrite. [Synthesis]
- Third-party queues exist (Graphite, Mergify) [Unverified].
- Frontier reference: Base Power describes footprint-based parallel queues, needing a hermetic build graph (they use Bazel); they report roughly 40% of merges skip revalidation [Blog: S23, re-open before relying]. Not applicable to a Yarn workspace repo without large changes. [Synthesis]

### 8.5 Retries and flaky tests

- The brief (A4) says no automatic retries.
- The tiered-CI blog suggests a bounded retry with flake logging and quarantine [Blog: S22].
- This is a policy choice, not something research settles.

### 8.6 Runners and capacity

- Vendor blog lists GitHub-hosted concurrency by plan (Free 20 concurrent jobs) [Vendor: S21, Unverified against GitHub docs]. At ~20 PRs a month, capacity is unlikely to matter. [Synthesis]

## 9. Rollout patterns

Three shapes, all with different risk:

1. **Hard cut** (the brief's choice): required from day one. Backlog freezes until fixed or closed.
2. **Observe first:** run the gate unrequired for a period, measure failures on real PRs, then make it required. Common practice in my experience, but I have **no source** for how common it is. [Synthesis]
3. **Staged by tier:** make fast checks required first, Docker tier later (or the reverse). [Synthesis]

Fact that affects any of them: adding a required check in branch protection is repo-wide and immediate for all open PRs. [Docs: S1 for required-check behaviour; "immediate for all PRs" is Synthesis]

## 10. POC and testing plan

### 10.1 GitHub mechanics that affect testing

- `pull_request` runs the workflow file from the PR's merge commit, so a workflow added inside a PR runs on that PR [Docs: S2].
- A re-run of an old run reuses the same merge commit, so it does not pick up newer main. A new commit creates a new merge [Docs: S3].
- So a workflow merged to main will not run on the 25 old PRs until each has a new event. `workflow_dispatch` with a ref input is one way to trigger manually. [Synthesis based on S3]

### 10.2 Fixture PRs (draft, never merged)

| Fixture | Change                                                      | Expected                                        |
| ------- | ----------------------------------------------------------- | ----------------------------------------------- |
| A       | Import of a package not in package.json (like PR #297)      | Fast tier fails on the dependency check         |
| B       | Dockerfile edited to break the build                        | Docker tier fails for that service only         |
| C       | Clean change touching two unrelated services                | Only those two run; gate green                  |
| D       | Change in shared package only                               | Dependents get selected (tests graph awareness) |
| E       | Docs-only change                                            | Everything skipped; gate green, not Pending     |
| F       | Change that makes one matrix leg fail and one get cancelled | Gate red                                        |

Fixtures are my design. [Synthesis]

### 10.3 Order of building (one possible order)

1. Skeleton workflow (trigger, concurrency, permissions, no-op job).
2. Detect job that only prints its output.
3. Fast tier, not required.
4. Docker tier, not required.
5. Aggregating gate job.
6. Run on the real backlog and count failures.
7. Decide about making it required.

Test the branch-protection step on a scratch repo first if one exists. [Synthesis]
