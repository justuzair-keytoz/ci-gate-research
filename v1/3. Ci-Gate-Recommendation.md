# CI Gate — Recommendation for Review

Purpose: a decision, not a catalog. The full options research lives in `ci-gate-research.md`; this distills it into what we'd actually build, why, and what needs sign-off first.

## The situation

Main has no automated validation today — all 14 workflows are manual-only, and 25 open PRs merge on human review alone. The failure mode that actually bites here is packaging, not logic: 12 Dockerfile-related commits in 6 months, because the real deploy artifact is a Docker image (`docker build -f UI/Dockerfile --target production`), not the native `yarn build` output. A gate that only runs native checks would report green while deploy still breaks.

## Recommendation

A hybrid, on three separate axes — not one tool, one pipeline shape, or one rollout switch:

1. **Depth:** fast native checks (lint, types, unit, dependency check) on every PR, plus a Docker image build validation scoped to only the services a PR touches.
2. **Rollout:** run the whole gate unrequired for a short period to measure real failure rate against the 25 open PRs, _then_ flip to required — rather than requiring it from day one.
3. **Build-parity:** start with a cheap read-only check that the gate's Docker build matches the real deploy build, with a shared build script as the near-term upgrade — not a full rebuild of the deploy pipeline.

Everything else below is either a single clear pick (change detection, matrix strategy, caching) or a staged path (build parity, rollout) rather than a fork we're leaving open.

## The five technical decisions

| Area                     | Recommendation                                                                                             |
| ------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Change detection         | `yarn workspaces foreach --since`, day one — zero new tooling                                              |
| Matrix + required checks | Dynamic matrix + a single aggregating gate job as the required check                                       |
| Docker build validation  | `docker/build-push-action` with `push: false`, `load: true`, GitHub Actions cache (`type=gha`, `mode=max`) |
| Gate/deploy build parity | Start with a parity check; shared composite action once the gate is trusted                                |
| Rollout                  | Non-required observe period, then flip to required once failure rate is known                              |

### 1. Change detection — `yarn workspaces foreach --since`

Already built into Yarn 4, no new tool to adopt or maintain ([Yarn CLI docs](https://yarnpkg.com/cli/workspaces/foreach)). Turborepo's `--affected` and Nx's `affected` do the same job with real dependency-graph awareness — they catch a downstream package affected by a shared-code change, which `--since` may not — but both mean adopting a build system the repo doesn't currently use ([Turborepo docs](https://turborepo.dev/docs/reference/run), [Nx docs](https://nx.dev/docs/features/ci-features/affected)). Not worth the lift just for this gate. **Caveat:** if `turbo.json` or `nx.json` already exists somewhere in the repo, this recommendation flips — build on what's there.

### 2. Matrix strategy + required checks — dynamic matrix, one gate job

At 14 services, a static per-service job list means editing the workflow every time a service is added — the same drift that produced today's 14 manual-only workflows. A dynamic matrix (a detect job emits JSON, a downstream job consumes it via `fromJson`) scales without file edits ([GitHub Docs](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/running-variations-of-jobs-in-a-workflow)).

The catch, and it's a real one: GitHub's own docs confirm that a job skipped by a conditional reports "Success," but a job that depends on a _failed_ job is skipped and does not report failure — so a naive required check on individual matrix legs can silently pass, or hang. Their fix is an `always()`-guarded job that aggregates the real result ([GitHub Docs, Troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)). That aggregating job — never the matrix legs themselves — is what gets marked required.

### 3. Docker build validation — build without pushing, GHA cache

`push: false` + `load: true` builds the image locally for a smoke test with no registry login at all. Paired with `type=gha` cache and `mode=max` (caches every layer of a multi-stage build, not just the final one), this needs zero AWS credentials — which matters, because the brief's constraint is no AWS access in PR runs ([Docker Docs, GHA cache backend](https://docs.docker.com/build/cache/backends/gha/); [Docker Docs, cache backends](https://docs.docker.com/build/cache/backends)).

ECR-backed caching was considered and ruled out for now: it needs AWS credentials to push cache layers ([AWS blog](https://aws.amazon.com/blogs/containers/announcing-remote-cache-support-in-amazon-ecr-for-buildkit-clients/)), which directly conflicts with the no-AWS-creds constraint. **Caveat:** GitHub Actions cache is capped at 10 GB per repo by default (admin-raisable since Nov 2025) and shares that budget with dependency caches — worth checking once both Dockerfiles are cached ([GitHub changelog](https://github.blog/changelog/2025-11-20-github-actions-cache-size-can-now-exceed-10-gb-per-repository/)).

### 4. Gate/deploy build parity — the one point that needs a scope call

This is the part that makes the gate meaningful rather than theater: if the gate builds with different flags than the real deploy build, a green gate doesn't predict a working deploy. The safest fix — one shared script or composite action that both the gate and the deploy workflow call — means editing the existing deploy workflow, which the brief marks out of scope.

Recommended staging: ship a **read-only parity check** first (a step that diffs the Dockerfile path, `--target`, and build-args declared in both workflows, and fails loudly if they've drifted). Zero risk to deploy, no permission needed. Treat the shared-action version as a fast-follow once the gate has earned trust — and flag it explicitly for sign-off when we get there, since it does touch deploy, even if only cosmetically.

### 5. Rollout — observe first, hard cut second

The brief's own open questions — do the 33 untested files pass, what's the real failure rate across the 25 PRs — can't be answered before the gate exists, and a same-day hard cut means finding out the answer by freezing the backlog. Standard sequencing: run the full gate as a non-required check against real PR traffic first, collect the failure data, _then_ flip it to required in branch protection. This isn't a delay — it's how the hard cut gets made safely instead of blindly.

## Where this lines up with wider industry practice

- **Tiered validation** (cheap/fast checks before expensive ones, with a dependency-manifest check specifically flagged as a fast, early-tier item) is showing up as the standard shape for CI under high PR volume — the exact pattern our hybrid depth already follows ([Breaking the CI Bottleneck](https://dev.to/tamizuddin/breaking-the-ci-bottleneck-architecting-pipelines-for-the-ai-code-era-hm), one team's account, not a formal standard).
- **PR-time vs. merge-time separation** — fast/blocking checks pre-merge, slow checks (e2e, deploy smoke tests) post-merge or nightly — is long-standing trunk-based-development practice, and matches our explicit exclusion of Playwright from this gate.
- **Merge queue** is the natural next step once required checks are stable (prevents two individually-green PRs combining into a red main), triggered via GitHub's `merge_group` event ([GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)). Out of scope now, but worth designing the gate workflow to add `merge_group` as a trigger later without a rewrite.

## Needs explicit sign-off before we start

- **Branch protection change is repo-wide and immediate** — the moment the gate job is marked required, every open and future PR is affected at once, not gradually. Worth a dry run on a scratch/forked repo first if one's available.
- **Any edit to the deploy workflow** — even the read-only parity check touches nothing, but the shared-composite-action upgrade (decision 4) does, and the brief marks deploy changes out of scope. Flagging now so it isn't a surprise later.
- **Retry policy** — the brief specifies no automatic retries for flaky checks; current industry guidance for AI-generated-code-volume pipelines increasingly favors a bounded retry with flake tracking instead. Real tension, not a research-settled question — needs a call.
- **Hard cut vs. observe-first** — recommending observe-first above; this reverses the design session's stated rollout and should be confirmed, not assumed.

## Still out of scope (unchanged from the brief)

Playwright/e2e in CI, Python CI tooling for RAG/Parser, changing the manual `workflow_dispatch` deploy process (beyond the parity check above), and merge queue / auto-merge.

## Open questions that would sharpen this further

Is Turborepo or Nx already used anywhere in the repo? Is `UI/Dockerfile` single- or multi-stage? Does the repo have a GHCR presence? How does the private npm token reach the Docker build today? Will fork PRs stay permanently absent (affects whether secrets-hardening is needed later)?
